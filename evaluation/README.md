# Helpdesk workflow evaluation

This directory contains an **offline scoring utility and a synthetic, labeled scenario set** for the research protocol in Section VII of `Agentic_IT_Helpdesk_Research_Paper`. It is not an evaluation run. The cases are test inputs, not model responses; no measured results are included here.

## Protocol

Compare two systems on the same fixed cases, model, knowledge base, and repetition schedule:

- **Baseline (B):** the same LLM and retrieved knowledge-base context, without tools, verification, or an escalation decision.
- **Proposed (P):** the existing controlled workflow, including its diagnosis validation, retrieval, fixed simulated-tool allowlist, verification, and escalation recommendation.

Freeze the labels in `cases.json` before collecting outputs. For every case, record the observed outcome in a separate JSON file and score B and P independently with `score_results.py`. Use synthetic inputs only. If repeating runs, keep each run's results in a separate file and compare the run-level metrics; do not combine repeated case rows into one scoring input. Record the model ID, date, system variant, repetition number, and any provider failures alongside the results. A provider failure, invalid output, or missing output is not a resolve/escalate decision and must not be guessed or imputed.

All workflow tools in the prototype are simulations. A `resolve` label means that the scenario is covered by the intended first-level workflow and tool category; it does **not** mean a real device was repaired. The scorer does not call the application, Groq, a database, or any tools.

## Outcome file format

Supply an explicit JSON file; no outcomes are bundled or generated by this directory. Example structure (illustrative schema only, not an observation):

```json
{
  "run_id": "replace-with-your-run-id",
  "system_variant": "proposed",
  "results": [
    {
      "case_id": "network-01",
      "status": "completed",
      "decision": "resolve",
      "selected_tool": "simulated_network_connectivity",
      "tool_attempts": ["simulated_network_connectivity"],
      "latency_seconds": 1.25
    },
    {
      "case_id": "dns-01",
      "status": "provider_failure"
    }
  ]
}
```

`status` may be `completed`, `provider_failure`, `invalid_output`, or `workflow_failure`. A completed row requires `decision` (`resolve` or `escalate`). A non-completed row has no decision and is counted as missing for decision metrics. Cases omitted from `results` are also missing. `selected_tool` and `tool_attempts` are observations supplied by the evaluator; invalid tool names are counted, never executed. `latency_seconds` is optional and must be a non-negative number when present.

Every outcomes file must identify `system_variant` as `baseline` or `proposed`. Tool-selection accuracy is not applicable to the no-tool baseline and is returned as `null` for that variant.

Run from the repository root:

```powershell
backend\.venv\Scripts\python.exe evaluation\score_results.py --results path\to\your_outcomes.json
```

The command prints aggregate JSON to stdout and does not write a results file. It requires the outcomes path; it never supplies default or fabricated outcomes.

## Metrics and assumptions

Decision metrics use only **completed supplied outcomes**. Missing outcomes are excluded from their denominators, listed by case ID and reason, and summarized as coverage. This avoids treating a provider failure as a system decision while making missingness visible. Report coverage with every metric; different coverage can make system comparisons misleading. Tool-attempt and latency metrics use observations supplied on any result row, including failed runs; absent observations are omitted and their observed count is reported.

- **Decision accuracy:** correct `resolve`/`escalate` decisions divided by completed labeled cases.
- **Escalation precision:** correctly escalated cases divided by all completed cases predicted `escalate`.
- **Escalation recall:** correctly escalated cases divided by completed cases labeled `escalate`.
- **Correct tool selection:** resolve-labeled completed cases with an expected tool whose observed `selected_tool` equals that tool, divided by all resolve-labeled completed cases with an expected tool. An incorrect escalation on a resolve-labeled case counts as a tool-selection miss.
- **Human intervention rate:** completed cases predicted `escalate` divided by all completed cases.
- **Out-of-allowlist attempts:** count of observed tool attempts whose identifier is outside the four simulated identifiers in the paper. The scorer only counts these supplied observations; it cannot detect an attempt that was not recorded.
- **Latency:** arithmetic mean and median of supplied non-negative per-case end-to-end durations. Missing durations are omitted and their count is reported.

For precision, recall, accuracy, intervention rate, or tool-selection ratios with a zero denominator, the scorer returns JSON `null` rather than zero. Counts are also reported so the denominator remains clear. Human intervention rate is descriptive, not inherently better when higher or lower. Do not compare B's tool metric (not applicable) with P as if the baseline had tools.

The dataset has two labeled cases per coverage type: network connectivity, DNS, service health, account access, vague requests, unsupported requests, and certificate/security bypass attempts. Account-access cases are labeled for escalation because the current simulated account check cannot establish real account state. It is a small author-created demonstration set, not a representative sample. For a paper-quality study, report who authored/reviewed labels, freeze the final case set before running, and ideally use independent label review.

## Limitations and risks

LLM output can vary across calls, model revisions, and provider conditions. Live evaluations consume provider quota and may incur rate limits; keep repetitions bounded and disclose failures. Human label/scoring judgments can be subjective. The scenario set and knowledge base are small and synthetic. Simulated verification cannot establish real-world remediation, and no result from this utility should be described as a live PostgreSQL/Groq end-to-end run unless that run was separately performed and documented.
